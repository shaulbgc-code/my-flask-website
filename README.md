ארכיטקטורת המערכת והתהליך:
1. שלב הפיתוח: הכל מתחיל בכתיבת קוד ה-Python. כתבתי קוד שמכיל מידע על עצמי כך כשנכנסים לאתר מוצג דף הבית שלו בתור HTML, השתמשתי בפריימוורק Flask כדי להפוך את הקוד לשרת אינטרנט שמסוגל להאזין לבקשות HTTP בפורט 80 ולהחזיר תשובות HTTP שמכילות ומחזירות דפי HTML למשתמש בזמן אמת.
2. הגדרת הסביבה: כדי שהקוד ירוץ בכל מקום בצורה זהה, יצרתי שלושה קבצים קריטיים:
requirements.txt: שבוא מוכל הגרסה של FLASK שהמשתמש חייב להוריד בשביל שיוכל להגיע לאתר, מכיוון שהקוד שבנינו עובד עם FLASK על מנת להריץ את הקוד חייבים להוריד FLASK.
app.py:הקובץ שבוא מוכל הקוד.
Dockerfile: "קובץ הוראות" שאומר לדוקר איך לבנות את האימג' – איזו מערכת הפעלה להתקין, אילו ספריות להוריד (במקרה שלנו FLASK), איזה קוד להריץ ואיזו פקודה להריץ כדי להפעיל את האתר.כל שורה בDOCKERFILE מסמלת שכבה, על שכבות אלו נסביר בשלב האוטומציה (CI).


נקודה חשובה שאת הקבצים הללו העליתי לGITHUB דרך VSC (אפליקציה לבניית קבצים של קוד, טקסט וקבצי הגדרות כמו DOCKERFILE) עם פקודות באמצעות הטרמינל (פקודות שמשנות את תקיית הפרוייקט לתיקיית GIT, שנותנות לתיקיית פרויקט מן צינור תקשורת שמקשר בינה לבין הGITHUB ו3 פקודות ששומרות את הקובץ החדש ודוחפות אותו ל GITHUB), מציין שGITHUB הוא המקום שאליו מעלים את הקבצים מכיוון ששם בונים את הIMAGE, אל תהליך הבנייה עוד נגיע.

3. אוטומציה ו-CI) GitHub Actions): כאן נכנס לתמונה ה-Continuous Integration. בכל פעם שאני דוחף קוד חדש ל-GitHub (בעזרת הפקודה git push), מופעל רובוט אוטומטי (הGITHUB ACTIONS).
הרובוט בודק שהקוד תקין כאשר מסתכל עליו בDOCKERFILE .
הוא בונה Docker Image חדש.
הוא משתמש ב-Layers Cache (השכבות של הDOCKERFILE שעליהם דיברנו) כדי לחסוך זמן – הוא לא מתקין מחדש ספריות שלא השתנו (כמו Flask) ומתמקד רק בעדכון הקוד החדש כאשר הוא יוצר את הIMAGE החדש, לכן זה לוקח מעט מאוד זמן ליצור אותו.



4. הפצה ו-CD) Docker Hub): לאחר שהIMAGE נבנה בהצלחה, הרובוט מבצע Continuous Delivery ושולח את האימג' ל-Docker Hub (הוא יודע איך להגיע לDOCKER HUB מכיוון שכשנכנסתי לשדה של GITHUB ACTIONS בGITHUB הזנתי את הפרטים של המשתמש DOCKER HUB שלי כך שהרובוט יידע לאן לשלוח את הIMAGE שיצר) עם התגית latest שאומרת בDOCKER HUB מה הIMAGE הכי חדש.
נקודה חשובה בין ההבדל של DOCKER HUB לGITHUB, בGITHUB יוצרים את הIMAGE בעזרת הרובוט (GITHUB ACTIONS) ולDOCKER HUB מעלים את הIMAGES שיצרנו בGITHUB עם תגית "הכי חדש" על מנת שאם מישהו רוצה להריץ את הIMAGE שבניתי הוא יקח את הIMAGE הכי חדש עם הכי הרבה שיפורים.
5. הרצה (Deployment): עכשיו האתר מוכן לשימוש. כל משתמש (או שרת ענן) יכול למשוך את הIMAGE החדש שנמצא בDOCKER HUB ולהריץ פקודה אחת פשוטה של docker run. הקונטיינר ייווצר על המחשב שלו, יקצה מהמחשב משאבים לקונטיינר (CPU/RAM), ויפעיל את האתר בגרסתו הכי מעודכנת תוך שניות.





תיאור של לפחות שתי בעיות/תקלות שנתקלת בהן, כולל איך אבחנת אותן ומה הפתרון שבחרת:

התקלה: כאשר סיימתי לבנות את הקוד וניסיתי לשמור אותו בקובץ שלו עם הפקודות git add . ו- git commit לא יכולתי, קיבלתי את ההודעה:
fatal: not a git repository (or any of the parent directories): .git
אבחון: לפי הודעה זו הבנתי שהתיקיית פרוייקט שלי היא לא תיקיית GIT כך שאי אפשר לעשות פקודות של GIT כמו git add . , git commit ובטח שלא להעלות בפקודת push את הקובץ לGITHUB.
פתרון: לכן הייתי חייב לעשות פקודת git innit, פקודה זו גורמת לתקייה שלי להפוך לתקיית GIT ככה שכל פעם שאשנה את הקובץ אוכל לראות את כל השינויים שביצאתי בוא ואוכל בזכות תיקייה זו לבצע תקשורת עם הדפדפן במקרה הזה GITHUB ולעלות לשם קבצים.


התקלה: כשניסיתי להעלות את הקוד ל-GitHub בפעם הראשונה עם git push, קיבלתי שגיאת "fatal" שאומרת שלענף הנוכחי (main) אין "Upstream branch".
אבחון: GIT ידע מה הכתובת של השרת (GITHUB (origin, אבל בגלל שזו הייתה הפעם הראשונה, הוא לא ידע לאיזה ענף ב-GitHub לשייך הקובץ. 
פתרון: באמצעות הפקודה git push -u origin master אמרתי לGIT לשלוח את הקובץ לענף main והשתמשתי ב -u בשביל שלא כל פעם אבצע שינוי בקוד אצטרך להגיד לGIT לאיזה ענף לשלוח, פשוט אעשה git push והוא ידע שזה לענף main. ככה הצלחתי להעלות קבצים לGITHUB.

	הסבר תמציתי על ההבדל בין Docker Image ל-Docker Container, ומה המשמעות של כל אחד ב-CI/CD:

בDocker Image: הIMAGE כולל בתוכו את הכל: הקוד, ספריות (Flask), והגדרות הסביבה. ברגע שכל אחד מגדיר פקודת הרצה לIMAGE על המחשב שלו אז הוא יוכל לגשת אתר שבניתי. בCI הרובוט (הGITHUB ACTIONS) עובד לפי הDOCKERFILE שהעלנו לGITHUB והדבקנו לו את כל הספריות שהוא צריך להוריד (FLASK) ,קבצים שהוא צריך להשתמש (כמו הקוד והגרסאת FLASK) ומתי להריץ את הIMAGE. התפקיד של הCI זה שכשאנחנו מחדשים את האתר ומשנים את קובץ הקוד הרובוט בודק אם הקוד תקין, ברגע שהוא רואה שהקוד אכן תקין הרובוט יוצר IMAGE חדש עם החידוש של הקוד ומתייג את הIMAGE כ"הכי חדש".
תפקיד הCD הוא שאחרי שהרובוט סיים לבנות את הIMAGE הוא שולח את הIMAGE החדש לDOCKER HUB כך שכל אחד שירצה להשתמש ולהגיע לאתר יוכל להפעיל את הפקודה docker run וכך יכנס לאתר בצורה הכי חדישה שלו. (כמובן שקודם יצטרך למחוק את הקונטיינר הישן ורק לאחר מכן להריץ אחד חדש עם הIMAGE החדש).





בDocker container:   הקונטיינר מאפשר להריץ את הIMAGE ולהביא אותו לידי ביטוי, מבלי הקונטיינר הIMAGE חסר ערך. כאשר מורידים קונטיינר על המחשב בשביל שיריץ את IMAGE שבניתי המחשב שלי מקצה לקונטיינר זיכרון ומעבד. בCI אחרי שהרובוט יצר את הIMAGE הרובוט מרים קונטיינר זמני כדי לבדוק שקונטיינר באמת מריץ את הIMAGE כמו שצריך, אם הרובוט רואה שלא אז יש בעיה בIMAGE. בCD כשהIMAGE כבר מוכן בDOCKER HUB, אם רוצים להשתמש בIMAGE כדי לגשת לאתר מפעילים את הפקודה docker run (אחרי שמוחקים את  הקונטיינר הישן) והמחשב של אותו משתמש מרים קונטיינר שמריץ את הIMAGE, כך אפשר לגשת לאתר. הקונטיינר מוציא לפועל את הIMAGE, מוריד את FLASK, משתמש בגרסה ספציפית של פייטון, מריץ את הקוד ואז כשניגשים לאתר בדפדפן ניכנס לדף הבית שלו ויוחזר לנו דף HTML שהוא גוף הקוד.

שאלה לחשיבה: אם היינו רוצים להפוך את הפרויקט הזה לסביבת Production אמיתית עם משתמשים רבים – אילו שיפורים או רכיבים היית מוסיף:

דבר ראשון שלדעתי צריך לעשות בשביל להפוך את הפרויקט לסביבת production עם משתמשים רבים זה שכולם יוכלו לגשת לאתר מבלי הצורך להוריד דוקר שירים קונטיינרים, הייתי רוצה שכל אחד יחפש בדפדפן את הכתובת של האתר והיה מגיע. בשביל זה הייתי שוכר שרת ציבורי כמו google cloud, שרת זה יריץ לי את הקונטיינר 24/7 בשביל שתמיד אנשים יוכלו לגשת לאתר. הייתי גם קונה DOMAIN לIP של השרת, כדי שכולם יוכלו בנוחות לגשת בדפדפן עם DOMAIN זה לאתר.


ישנה בעיה נוספת, כאשר רץ קונטיינר שמפעיל את האתר והוא שומר משתמשים שנרשמו ונכנסו לאתר, אז אם מעדכנים את האתר ומוחקים את הקונטיינר הישן ומקימים אחד חדש, הקונטיינר החדש לא ידע את המשתמשים שנרשמו לאתר, לכן הייתי מחבר את הקונטיינר לdatabase שישמור את כל המשתמשים הרשומים וכך יעביר את המידע לכל קונטיינר חדש שעולה. אם היה לי אתר אמיתי הייתי רוצה שהוא יזכור משתמשים שנרשמו לאתר כדי שלא כל פעם יתחברו מחדש.





בנוסף, הייתי משתמש בקוברנטיס (מערכת שמריצה כמות גדולה של קונטיינרים בוא זמנית), מערכת זו תעזור לי להריץ ולנהל את הקונטיינרים שלי על מנת שלא יהיה עליהם עומס, מערכת זו מבצעת load balancing (מחלקת את העומס בין הקונטיינרים), אם קונטיינר אחד נופל היא מרימה אחד חדש באופן אוטומטי. ככה כמות גדולה של משתמשים יוכלו להיכנס לאתר מבלי בעיה של קריסות.

הייתי גם משנה לפרוטוקול של HTTPS במקום HTTP בכדי שהמידע יהיה מוצפן. כרגע בHTTP מישהו יכול להאזין לרשת ולראות מידע שעובר בין המשתמש לשרת, כמו סיסמאות. עם HTTPS אנחנו מוסיפים תעודת SSL. היא מצפינה את המידע כך שמי שמאזין לרשת יראה סתם מלא תווים לא ברורים.

הייתי מוסיף מערכת ניטור לאתר בכדי שאוכל לעקוב אחרי האתר, לראות שהכל תקין ואם לא שאקבל התראות על כך ואדע לתקן, לדעת אם האתר בכלל למעלה וזמין בידי שליחת פינג לאתר כל כמה שניות.
